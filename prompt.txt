# FLOWFORGE — STAGE 1 IMPLEMENTATION

You are the implementation engineer for Stage 1 of FlowForge.

## PROJECT

FlowForge is a distributed job orchestration platform.

The final system will eventually support:

* asynchronous job execution
* multiple workers
* retries
* exponential backoff
* dead-letter queues
* worker leases
* crash recovery
* scheduling
* priorities
* rate limiting
* workflow/DAG execution
* idempotency
* observability
* Docker
* CI/CD
* Kubernetes/cloud deployment

BUT THIS TASK IS ONLY STAGE 1.

Do not implement future-stage functionality unless it is required to keep the architecture extensible.

---

# STAGE 1 OBJECTIVE

Build the smallest useful version of FlowForge:

Client
→ Go REST API
→ PostgreSQL
→ Redis Stream
→ Worker
→ PostgreSQL

The system must allow a client to submit a background job, have a worker execute it, and query the job status/result.

---

# TECHNOLOGY

Use:

* Go
* PostgreSQL
* Redis
* Docker
* Docker Compose
* GitHub Actions

HTTP framework:

Prefer the Go standard library or Chi unless there is a strong reason to use something else.

Database:

Use PostgreSQL with pgx.

Redis:

Use Redis Streams.

Do not introduce Kafka yet.

Use a conventional SQL migration approach such as goose or another lightweight migration tool. Explain the choice in documentation.

---

# IMPORTANT ARCHITECTURAL PRINCIPLE

The architecture must remain modular.

Do not put business logic directly inside HTTP handlers.

Do not put database logic inside workers.

Do not tightly couple task execution to Redis.

Separate:

API layer
↓
Job service
↓
Repository
↓
Queue abstraction

and:

Worker
↓
Queue consumer
↓
Task registry
↓
Task handler
↓
Job repository

Future stages must be able to replace or extend individual components.

---

# JOB FLOW

POST /jobs should roughly perform:

1. Validate request.
2. Create job in PostgreSQL.
3. Publish a job message to Redis.
4. Update job state to QUEUED.
5. Return job ID.

The system has a known dual-write limitation between PostgreSQL and Redis.

Do NOT solve this with a transactional outbox in Stage 1.

Document this limitation explicitly because the transactional outbox will be introduced in a later stage.

If Redis publishing fails after the PostgreSQL insert, the job may remain PENDING.

Do not hide or fake reliability that does not exist.

---

# REDIS MESSAGE

A queue message should contain enough information for a worker to locate the job.

Example:

{
"job_id": "...",
"type": "echo"
}

Do not place unnecessary duplicated business state in Redis.

PostgreSQL remains the source of truth for job state.

---

# WORKER

Create a separate executable:

cmd/worker

The worker should:

1. Connect to PostgreSQL.
2. Connect to Redis.
3. Create/verify its consumer group.
4. Block waiting for jobs.
5. Receive a job.
6. Load the job from PostgreSQL.
7. Mark it RUNNING.
8. Execute the registered task handler.
9. Store result or error.
10. Mark job COMPLETED or FAILED.
11. Acknowledge the Redis message.

Do not build worker pools yet.

Only one worker process and one consumer are required in Stage 1.

---

# TASK SYSTEM

Do not hard-code all task logic inside the worker.

Create a task handler abstraction.

For example conceptually:

TaskHandler interface

with something like:

Handle(ctx, payload) → result/error

Create a task registry.

Initially implement only:

1. echo
2. sleep

The echo task returns the supplied message.

The sleep task waits for a requested number of seconds and then returns successfully.

This allows the system to demonstrate actual asynchronous execution.

Validate payloads.

Do not execute arbitrary code supplied by users.

---

# ERROR HANDLING

Handle:

* invalid JSON
* missing required fields
* unknown job type
* job not found
* PostgreSQL failure
* Redis failure
* task failure
* malformed task payload

Return sensible HTTP status codes.

Use structured application errors internally.

Do not leak database or internal implementation details through the API.

# FAILURE LIMITATIONS TO DOCUMENT

Stage 1 deliberately does NOT guarantee recovery from:

* worker crashes
* duplicate execution
* Redis failure between enqueue and processing
* PostgreSQL/Redis dual-write inconsistency
* abandoned RUNNING jobs

These become later stages.

Do not pretend Stage 1 is production fault tolerant.

# FINAL ACCEPTANCE CRITERIA

Stage 1 is complete only when:

1. `docker compose up --build` successfully starts the system.
2. API accepts a job.
3. Job appears in PostgreSQL.
4. Job is published to Redis.
5. Worker consumes it.
6. Worker executes the registered task.
7. Job becomes COMPLETED.
8. Result is persisted.
9. Failed task becomes FAILED.
10. GET /jobs/{id} returns correct state.
11. GET /jobs supports pagination.
12. Health/readiness endpoints work.
13. Integration tests pass.
14. `go test -race ./...` passes.
15. CI passes.
16. README is accurate.
17. Stage documentation exists.
18. Architecture diagram exists.
19. API specification exists.
20. Demo script works.

Do not move to Stage 2 until every acceptance criterion is satisfied.

After finishing, stop and produce a Stage 1 completion report rather than beginning Stage 2.
