# STAGE 2A — TRANSACTIONAL OUTBOX

Change job creation from:

DB insert
→ Redis publish

to:

BEGIN DATABASE TRANSACTION

INSERT job as PENDING

INSERT outbox event

COMMIT

No Redis interaction should happen inside the API request after the transaction.

The API should return success once the durable PostgreSQL transaction has committed.

---

# OUTBOX TABLE

Create a migration for:

outbox_events

Recommended fields:

id
aggregate_id
event_type
payload
status
attempts
last_error
created_at
published_at

Use appropriate constraints and indexes.

At minimum consider efficient lookup of pending events.

Do not over-engineer the schema.

---

# OUTBOX EVENT

For job publication, define an event such as:

JOB_CREATED

Payload should contain enough information for the dispatcher to publish the Redis message.

Avoid duplicating unnecessary job state.

PostgreSQL remains the source of truth.

---

# TRANSACTIONAL GUARANTEE

The important guarantee is:

Either:

job exists
AND
outbox event exists

or:

neither exists.

This eliminates the Stage 1 failure where the job can exist without a durable record of the required publication.

Document this.

Do not claim exactly-once publication.

---

# STAGE 2B — OUTBOX DISPATCHER

Create a separate executable:

cmd/dispatcher

The dispatcher:

1. polls pending outbox events
2. claims/locks events safely
3. publishes them to Redis Streams
4. records successful publication
5. records publication errors
6. continues processing future events

Use PostgreSQL mechanisms appropriate for concurrent polling.

Investigate:

SELECT ... FOR UPDATE SKIP LOCKED

before implementation.

The design must be safe if multiple dispatcher instances eventually exist, even though Stage 2 may run one dispatcher locally.

---

# IMPORTANT FAILURE CASE

Handle:

Redis publish succeeds
→ dispatcher crashes
→ DB transaction marking outbox event PUBLISHED never commits

On restart the event may be published again.

This is expected.

Therefore Stage 2 uses:

AT-LEAST-ONCE PUBLICATION

not exactly-once publication.

Document this clearly.

Do not hide duplicate publication.

---

# DUPLICATE MESSAGE HANDLING

Workers must safely handle duplicate Redis messages.

Use atomic database state transitions.

For example:

A job may only be claimed if its current state permits claiming.

The worker must NOT execute a completed job again simply because a duplicate Redis message arrives.

The implementation must distinguish:

- first legitimate delivery
- duplicate delivery
- stale delivery

Do not introduce user-level idempotency keys yet.

This is only delivery deduplication using job state/concurrency control.

# RETRYABLE VS PERMANENT ERRORS

Task execution errors need a way to communicate whether retrying makes sense.

Introduce a small explicit abstraction.

Example:

TaskError:
- Err
- Retryable

The exact interface can differ if you have a cleaner Go design.

Rules:

Retryable error
→ retry if attempts remain

Permanent error
→ FAILED immediately

Unknown/unclassified errors
→ follow a documented default policy

Do not retry invalid task payloads indefinitely.

---

# RETRY STATES

Introduce a state:

RETRY_WAIT

State lifecycle:

PENDING
→ QUEUED
→ RUNNING
→ COMPLETED

or:

RUNNING
→ RETRY_WAIT
→ QUEUED
→ RUNNING

or:

RUNNING
→ FAILED

after retries are exhausted or the error is permanent.

Update the domain transition model and database transition guards.

---

# RETRY POLICY

Support:

max attempts

Use:

max_attempts = 3

as the default unless configuration already has a better established default.

Do not hard-code policy in multiple places.

Centralize retry calculation.

---

# EXPONENTIAL BACKOFF

Implement:

delay = min(base_delay * 2^(attempt-1), max_delay)

Example:

1 sec
2 sec
4 sec
8 sec

Use configurable:

base delay
maximum delay

Consider optional jitter.

Document why jitter reduces synchronized retry bursts.

---

# RETRY TIMING

Do NOT build the full general scheduler in Stage 2.

Retry timing only needs to support retryable jobs whose:

next_attempt_at <= now

are eligible to be re-queued.

Reuse the existing outbox/dispatcher architecture where possible.

The purpose is retry timing, not cron scheduling.

Document this distinction.
